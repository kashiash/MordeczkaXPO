TL;DR

Dochodzi encja AppearanceRule (reguła wyglądu jako dane) i ViewController, który przy każdej aktywacji widoku czyta reguły z bazy i wstrzykuje je do AppearanceController.CollectAppearanceRules — bez bufora w pamięci procesu, więc trzy repliki propagują zmiany za darmo.

Regułę tworzy asystent AI dwoma narzędziami (sprawdz_regule_wygladu / utworz_regule_wygladu), a poprawia człowiek na własnym ekranie w grupie „Zarządzanie schematem".

Sednem jest jeden walidator w trzech miejscach: odmawia zapisu bubla, pomija niesprawną regułę zamiast wywalić widok i pokazuje na ekranie reguł, że jest zepsuta i dlaczego.

Kolor zapisujemy jako rolę semantyczną, nie ARGB — odcień rozwiązuje się przy renderowaniu. Wdrożenie: zgaszenie trójki replik, nowy obraz, --updateDatabase, trzy-repliki.sh, test osobno na 8101/8102/8103.

Paleta ról i parsowanie koloru — dwie pułapki do ominięcia

Kolejność rozstrzygania: 1. nadpisanie administratora (oba kolory ustawione i sparsowane) → 2. rola → 3. nic (null, nigdy Color.Empty). Przypadek połowiczny rozstrzygnięty jawnie: nadpisanie z jednej strony jest ignorowane w całości i reguła spada na rolę; walidator wystawia Warning.

BłądOstrzeżenieSukcesInformacjaWyciszoneWyróżnione

  1. int.Parse(…, NumberStyles.HexNumber) przepełnia się dla alfy ≥ 0x80. Konwerter Fleetmana robi dokładnie to i rzuca OverflowException na każdym nieprzezroczystym kolorze — bez try/catch. Używamy uint.Parse + Color.FromArgb(unchecked((int)value)) w try/catch.
  2. Brak wartości musi wracać jako null, nie Color.Empty. Color.Empty.Name to "0" i cicho przechodzi przez filtry — błąd obecny i we Fleetmanie, i w DataDrive.

Tekst dosłowny do wstawienia 
## Appearance Rules (colouring rows and fields)

- An appearance rule paints records in a list or on a detail screen when a criteria expression matches. Reach for these tools when the user talks about kolor / kolorowanie / podświetl / na czerwono / wyróżnij / wyszarz / oznacz, or dictates something like "zrób faktury niezapłacone na czerwono na listach".
- Tools: `sprawdz_regule_wygladu` (read-only check) and `utworz_regule_wygladu` (validates again, then saves).
- **NEVER guess the parts the user did not say.** Before calling `utworz_regule_wygladu` you must know all three: (1) which entity, (2) the criteria expression, (3) the colour role. If any is missing, ask ONE specific question about it and wait for the answer.
- Translate the user's words into a criteria expression yourself, but ONLY over properties that actually exist on the entity — call `describe_entity` or `sprawdz_regule_wygladu` to check. "Niezapłacone" may be `[Zaplacona] = False` on one entity and `[DoZaplaty] > 0` on another; when both are plausible, say which one you picked and why, and let the user correct you.
- If a tool answers PROBLEM because a property does not exist, do NOT ask the user which field to use — the answer lists the entity's real fields. Pick the closest one, propose it in one sentence, and wait for a yes.
- Colour is a semantic ROLE, never a hex value. The six roles are: Error (needs action — overdue, unpaid, rejected), Warning (deadline approaching, data missing), Success (settled, closed well), Info (neutral emphasis), Muted (archived, cancelled, less important), Highlight ("look here", no judgement). Never invent a role — ask. Raw colours exist, but only an administrator sets them on the rules screen, and you must not offer to do it.
- `targetItems` is `*` (the whole row) unless the user names specific fields. `context` is `ListView` unless the user is clearly talking about a record screen.
- When two rules paint the same field, the one with the higher `priority` wins. Say so if the user creates a second rule over the same field.
- Appearance rules are DATA, not schema: no Deploy, no restart, no rebuild. After creating one, tell the user to refresh the page (F5) and open the list. Also tell them the rule can be switched off or corrected under „Zarządzanie schematem → Reguły wyglądu" — that screen is how a mistake gets undone.
- A rule survives on its own: if the entity it points at is deleted or renamed, the rule stops colouring and is shown as „Niesprawna" on the rules screen instead of breaking the view.

Zachowanie kontrolera

Module/Controllers/AppearanceRuleViewController.cs, klasa ObjectViewController<ObjectView, object>. Kontrolery w Module/Controllers/*.cs są wykrywane automatycznie — żadnej rejestracji w Startup.cs po żadnej ze stron, dlatego parytet Blazor/WinForms wychodzi za darmo.

OnActivated:
 1. base.OnActivated()
 2. Strażniki — każdy kończy metodę bez efektu:
    – View is not ObjectView
    – View.ObjectSpace is NonPersistentObjectSpace   // dopasowanie WZORCEM, nie GetType() != typeof(...)
    – View.ObjectSpace.IsDisposed
    – View.ObjectTypeInfo?.Type == null
 3. LoadRules()                       // CAŁOŚĆ w try/catch → pusta lista + log
 4. lista pusta → koniec, nic nie subskrybujemy
 5. appearanceController = Frame.GetController<AppearanceController>()   // null → log i koniec
 6. appearanceController.ResetRulesCache()
 7. appearanceController.CollectAppearanceRules += OnCollectAppearanceRules
 8. appearanceController.Refresh()

Kolejność kroków 6–8 jest nienegocjowalna. Pominięcie ResetRulesCache() sprawia, że zdarzenie w ogóle się nie odpala: DevExpress zacache'ował „brak reguł dla tego typu" z pierwszej, bezregułowej aktywacji widoku. Tę samą kolejność mają wszystkie cztery aplikacje referencyjne.

LoadRules()  — jedyne miejsce, w którym rozmawiamy z bazą
 1. Przestrzeń obiektów z INonSecuredObjectSpaceFactory, zwalniana w OnDeactivated
 2. Zapytanie: IsEnabled = True            -- JEDYNY filtr w bazie; NIGDY po Health
 3. W pamięci, dla każdej reguły:
    a. type = rule.ResolveTargetType();  null → pomiń
    b. !type.IsAssignableFrom(View.ObjectTypeInfo.Type) → pomiń
    c. ViewId ustawiony i != View.Id → pomiń
    d. Validator.Check(...).Health == Broken → pomiń + log
 4. OrderBy(Priority).ThenBy(Name).ThenBy(Oid)          -- deterministycznie
 5. Zapis do pola _rules

Health i Diagnosis NIE MOGĄ być filtrem w zapytaniu. To metadane do pokazania człowiekowi, nie bramka wykonawcza — jedyną bramką jest żywe sprawdzenie w kroku 3d. Gdyby zapytanie odsiewało po Health <> Broken, reguła oznaczona jako niesprawna w oknie graduacji nigdy nie zostałaby ponownie oceniona po wklejeniu źródła i przebudowie — kolorowanie nie wróciłoby samo, wbrew kryterium A-23. Ta sama zasada broni każdego przypadku, w którym typ staje się rozwiązywalny bez udziału człowieka: restart repliki, wdrożenie, cofnięcie graduacji.

Dlaczego niezabezpieczona przestrzeń obiektów. Reguła wyglądu to konfiguracja interfejsu, nie dane użytkownika. Czytanie jej przez zabezpieczoną View.ObjectSpace oznaczałoby, że użytkownik bez uprawnienia dostaje pustą listę i kolorowanie umiera dla niego po cichu. Cena: odczyt konfiguracji UI omija uprawnienia — akceptowalna, bo nie wypływa z niej żadna dana biznesowa.
Świadome odstępstwo od Fleetmana. Fleetman ładuje reguły leniwie, w środku handlera. U nas zapytanie jest w OnActivated i nigdy w handlerze — CollectAppearanceRules odpala się raz na element interfejsu, więc zapytanie w środku byłoby katastrofą wydajnościową. 
private void OnCollectAppearanceRules(object sender, CollectAppearanceRulesEventArgs e)
{
    try
    {
        if (_rules == null || _rules.Count == 0) return;
        e.AppearanceRules.AddRange(_rules);        // List<IAppearanceRuleProperties>
    }
    catch (Exception ex) { _log(ex); }            // nigdy nie wypuszczamy wyjątku
}
  • Żadnego zapytania do bazy w handlerze. Odpala się raz na każdy element interfejsu.
  • try/catch obejmuje całe ciało. Nieobsłużony wyjątek tutaj wywraca cały widok, nie jedną komórkę.

Na widokach samych reguł działają dwa kontrolery naraz — i tak ma być. AppearanceRuleViewController jest typu ObjectViewController<ObjectView, object>, więc aktywuje się także na liście i szczegółach AppearanceRule, obok kontrolera edytora. Po zapisie oba wykonają ResetRulesCache() + Refresh() na tej samej ramce — dokładnie to podwojenie, które notatka porównawcza wytyka Brekhofowi. Tu jest nieszkodliwe i nie jest błędem do naprawienia przez usunięcie którejś subskrypcji: zdejmując pierwszą, tracimy kolorowanie niesprawnych wierszy; zdejmując drugą — natychmiastowe odświeżenie po edycji.

Odświeżanie po zapisie robi drugi, mały kontroler na widokach samych reguł: na ObjectSpace.Committed (nigdy OnSaving) resetuje cache własnej ramki i woła Refresh(). Żadnego rozgłaszania — statyczny event RulesCommitted Brekhofa jest tu podwójnie bezużyteczny: trzy repliki to trzy procesy, a w Blazor Server zapis jednej osoby odpalałby zapytanie u wszystkich pozostałych, poza dyspozytorami ich obwodów.

Uprawnienia, Updater.cs i wdrożenie

Żadna zmiana w Updater.cs nie jest wymagana

  1. Kolorowanie nie przechodzi przez system bezpieczeństwa — kontroler czyta reguły niezabezpieczoną przestrzenią obiektów, więc działa dla każdego zalogowanego.
  2. Ekran reguł jest dostępny dla administratora bez wpisu — rola Administrators ma IsAdministrative = true i omija sprawdzanie uprawnień. Tak samo są dziś dostępne CustomClass i WorkflowDefinition z tej samej grupy.
  3. Blok w Updater.cs na wdrożonej instancji nie istnieje — zweryfikowane w paczce: "Release" + 7 bajtów IL. Empirycznie potwierdzono też, że SDK .NET definiuje symbol RELEASE przy -c Release, więc to reguła, nie przypadek jednej paczki.

Gdyby mimo to rola Default miała dostać ekran, wpisy muszą stanąć poza #if !RELEASE i poza blokiem if (role == null). Rejestracja typu to jedna linia: AdditionalExportedTypes.Add(typeof(BusinessObjects.AppearanceRule));. QueryMetadata / GetMetadataFingerprint zostają nietknięte.
